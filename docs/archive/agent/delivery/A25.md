# A25 交付：多标签页刷新令牌不互相清空

## 1. 实现摘要

- `app/src/api.ts`：把 `tryRefresh` 里的实际刷新拆成 `refreshOnce(gen, srv, rt)`；有 `navigator.locks`（Web Locks）时经 `navigator.locks.request("chat_token_refresh", …)` 串行化，拿到锁先重读 `localStorage` 里的刷新令牌——已被换成别的值（别的标签页刚刷新成功或新登录）就直接当作成功、用存储里的新访问令牌重试，不再请求服务端。无锁环境走同一条 `refreshOnce`：刷新请求失败（非 2xx 或网络异常）后再判一次令牌是否已被换掉，是则同样算成功。只有令牌没被换掉且服务端拒绝才返回失败，`call()` 才 `clearSession()` + 派发 `chat:logout`。锁服务本身抛错时退化为无锁刷新。
- `app/src/api.test.ts`：`// ===== Agent A25 =====` 三个用例（无锁退路保留新令牌、Web Locks 串行化只发一次刷新、令牌未换+401 仍清会话）；另有 1 行改动——既有用例 `keeps refresh promises and finalizers isolated across generations` 桩 `navigator = {}`，因为 Node ≥21 自带真实 `LockManager`，不桩的话旧 gen 的未完成刷新会一直占着真锁，新 gen 的刷新排队而等不到发起（这正是本票要的行为，但该用例测的是无锁路径的代次隔离）。

只改了 `app/`；无迁移、无服务端改动。

## 2. 接口契约

无新增/变更的 REST、WS 帧或表结构。前端内部行为：

- `tryRefresh` 返回值语义不变（`true` → `call()` 用当前 `localStorage` 里的访问令牌重试原请求），但下列情形现在也返回 `true`：
  - 进入刷新时（拿到 Web Locks 后）发现 `chat_refresh` 已被换成别的非空值；
  - 刷新请求失败后发现 `chat_refresh` 已被换成别的非空值；
  - 刷新响应到手、写回前发现 `chat_refresh` 已被换掉（不覆盖别人的新凭据，直接复用）。
- 返回 `false` 的情形：`chat_refresh` 仍是本次刷新开始时的那个值（或为 `null`，即被清空）且刷新请求未成功。此时 `call()` 维持原逻辑：清会话 + 派发 `chat:logout` + 抛 `ApiError(401)`。
- 会话代次语义不变：`gen !== session()` 或 `getServer()` 变化时仍返回 `false`，旧代次绝不把旧凭据写回。
- 锁名 `chat_token_refresh` 为同源内共享；本应用 localStorage 里只有一个服务器槽位，无需按服务器分锁。
- 旧客户端兼容：纯前端行为，无协议变化。

## 4. 未覆盖项与已知限制

- 无 Web Locks 的浏览器里仍存在一个残余窗口：本标签页的刷新 401 与另一标签页写回新令牌若恰好在同一微任务窗口内交错，本标签页可能仍误判失效而清会话。退路只能收窄不能消除该窗口；要彻底串行必须靠 Web Locks（现代浏览器、Node ≥21 的 webview 均支持）。这是任务单「退路」条款的固有边界。
- 刷新期间的网络异常（fetch 抛错而非服务端 401）且令牌没被换掉时，仍按失败处理（清会话）——与改动前语义一致，未放宽为「网络错不清会话」。
- 「令牌被换掉」只区分「换成别的非空值」与「被清空（null）」：别的标签页登出/清空存储时，本标签页仍走正常登出路径。换成别人新登录的令牌也视为成功并直接复用（同源标签页本就共享同一账号态；跨标签页同步登出/登录按任务单「不做」节明确排除）。
- 用「换成新值」判成功时不验证新访问令牌：若重试原请求仍 401（如新令牌也失效），`call()` 维持原逻辑清会话+登出。
- 真锁排队存在理论上的等待：同一页面里旧代次刷新的 fetch 若长时间不结束，新代次的刷新会排在锁后等它 settle；正常网络下 fetch 很快返回，影响可忽略。
