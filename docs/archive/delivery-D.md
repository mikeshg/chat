## 1. 已复现的问题

以下问题有当前代码运行、真实浏览器交互或命令执行证据；不是仅根据阶段报告推断。

### High

#### H1. 匿名投票创建重放泄露创建者选择

- **位置**：`server/src/domain.rs:555-568,796-826`；`server/src/api.rs:1171-1175`；`server/src/ws.rs:348-351`。
- **复现**：两个专用测试用户在私有群中对匿名投票选择不同选项，只有创建者添加 reaction；再次提交创建者原来的 `client_msg_id`。
- **实际**：REST 创建重放与 WS 共享创建键重放均向另一成员发送创建者的 `my_option_ids`，并把 `reacted_by_me` 设为 true；该成员自己的历史 API 返回的本人字段仍是正确值。虽然 `voters` 数组为空，但结合消息发送者可识别创建者的匿名选择。
- **对照**：重放没有重复消息或推进 seq，因此只检查幂等消息数量会漏掉隐私问题。
- **修复方向**：重放只回发起者 ACK，或广播时逐接收者计算完整视图；不能把创建者视图广播全群。
- **回归要求**：创建→不同用户投票/表态→同键重放，分别检查所有接收者字段，而不是仅检查匿名 voters 数组。

#### H2. 历史升级会丢失消息附件关联

- **位置**：`server/migrations/0005_sync_invariants.sql:11-21`。
- **复现**：在专用空库执行 0001–0004，插入三条共享同一附件的消息（包含相同 created_at 的两条），再原样执行 0005–0009。
- **实际**：SQL 升级全部成功；消息数保持 3，但有附件关联的消息从 **3 变为 1**，读模型也只剩 1 条附件。
- **影响**：历史消息失去附件访问入口，不是“唯一索引可以创建”就等于兼容升级；当前迁移没有保留丢失映射。
- **修复方向**：保留每条消息与附件的关联，例如拆分附件记录且正确保留共享物理路径；不得直接改已经执行的旧迁移或重建现有库掩盖问题。
- **回归要求**：真实旧数据夹具验证每条历史消息仍可访问附件；另测删除一条共享路径引用不会影响其他引用。

#### H3. 部署用冻结依赖安装失败

- **位置**：`app/package.json:24`；`pnpm-lock.yaml:19-37`；`server/Dockerfile:7`。
- **命令**：`pnpm install --lockfile-only --frozen-lockfile --offline --ignore-scripts`。
- **实际**：`ERR_PNPM_OUTDATED_LOCKFILE`，manifest 新增 `vitest@^3.2.4`，pnpm lock 未记录；生产 Dockerfile 的 frozen install 同样受影响。
- **修复方向**：统一项目的 pnpm 锁文件并验证干净安装；另有 `app/package-lock.json` 的本地 pnpm 目录链接，不能作为可移植安装方案。
- **验收边界**：本轮 pnpm 运行测试时自动补装了依赖，导致现有 node_modules 可构建；这不改变原冻结安装失败结论。自动产生的 pnpm-lock 内容及换行副作用已撤回至原内容，没有顺手修复锁文件。

### Medium

#### M1. 迟到的目录或创建消息会回退会话预览

- **位置**：`app/src/store.ts:194-243`。
- **复现**：缓存同一消息的 edit/delete v3，再将相同 id/seq 的 v0 分别送入 `mergeConversationLists` 和 `applyLiveMessage`。
- **实际**：线程仍保留 v3，`last_message` 却变回 v0，包括已删除正文再次出现在会话预览。四个定向案例均失败。
- **修复方向**：同一消息的预览合并也比较 edit_version；seq 仅用于不同消息排序，不能替代变更版本。

#### M2. 迟到偏好会撤销已确认的静音/归档

- **位置**：`app/src/store.ts:141-154,194-213`。
- **复现**：先应用较新 updated_at 的永久静音+归档，再从偏好帧或目录响应应用较旧未静音/未归档值。
- **实际**：两个入口都回退到旧状态，`mute_forever=false`、`archived_at=null`。
- **修复方向**：偏好独立进行可靠的版本/时间新旧判定，并覆盖迟到 PUT、WS 与目录响应交错；时间字段需保证服务端排序语义。

#### M3. 编辑/删除原消息后，已加载引用仍显示旧正文

- **位置**：`app/src/store.ts:292-304`；`app/src/ui/ChatView.tsx:636-647`。
- **真实浏览器**：发送原文→回复→编辑原文→删除原文；原消息正确变成“消息已删除”，引用按钮仍为原来的正文，没有变成“原消息已删除”。
- **状态测试**：编辑/删除两个案例中，被回复消息版本已更新，引用消息的 preview 仍为旧 excerpt、`deleted=false`。
- **补充观察**：真实重启后客户端重连刷新，引用才恢复为“原消息已删除”。这是在线更新缺口，不是永久数据库数据残留。
- **修复方向**：接受源消息变更时同步刷新依赖引用，或优先从最新缓存源消息派生显示；覆盖在线情形，不能只重查服务端历史。

#### M4. 投票到期后按钮仍可点击且不会自行恢复正确状态

- **位置**：`app/src/ui/PollCard.tsx:29-46,97`。
- **真实浏览器**：加载 15 秒后截止的投票，跨过截止时间；检查时服务器历史返回 `expired=true`，卡片仍显示可点击选项/关闭按钮。
- **实际**：点击后 REST 正确返回 409，UI 显示 `poll is closed`，但按钮仍未禁用。重连刷新后才显示“已截止”。
- **修复方向**：截止时刷新权威状态；冲突后回读状态，并继续保留服务端过期拒绝逻辑。

#### M5. 创建投票已提交但响应丢失，点击重试会再创建一条

- **位置**：`app/src/ui/NewPollModal.tsx:50-56`。
- **真实浏览器受控故障注入**：仅拦截一次本地测试页面的创建响应，真实服务器返回 200 后对 UI 模拟响应丢失；保留弹窗内容，再点击“发起投票”。之后恢复原 fetch。
- **实际**：第一次服务器已存在 1 条，重试后成为 **2 条不同 id、seq=5/6 的投票**；UI 同样显示两张卡片。
- **修复方向**：不确定结果重试复用相同创建键和请求内容，明确开始新操作时才分配新键。
- **测试缺口**：服务端重复相同 key 的测试不会发现 UI 每次生成新 key 的问题。
