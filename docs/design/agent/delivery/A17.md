## 2. 接口契约

### 表 `agent_schedules`

`id`、`agent_id → agents ON DELETE CASCADE`、`owner_id → users ON DELETE CASCADE`、`name`（1–40）、`prompt`（1–4000）、`target_conversation_id → conversations ON DELETE CASCADE`、`spec jsonb`、`timezone`、`enabled`、`next_run_at`、`last_run_at`、`created_by`（`user` / `agent`）、`created_at`。

另外有 `disabled_reason text NULL`（任务单没有这一列）。停用原因要能被列表看到：`owner_disabled`、`agent_deleted`、`not_member`、`bad_spec`。重新启用并算出下一次后清空。

每个主人最多 50 条，应用层 `400 too_many`（创建时锁住用户行再计数）。

`spec` 四种：

- `{"type":"once","at":"<RFC3339>"}`
- `{"type":"daily","time":"09:00"}`
- `{"type":"weekly","days":[1,3,5],"time":"09:00"}`（1 = 周一，存库时升序去重）
- `{"type":"interval","minutes":N}`（5 ≤ N ≤ 5256000，上限是为了不让间隔溢出）

`once` 的 `at` 不在未来 → 创建 `400 bad_spec`。钟点必须是 `HH:MM`。时区必须是 IANA 名。

### `agent_invocations`

`trigger_message_id` 可空，`schedule_id → agent_schedules ON DELETE SET NULL`。二者至少有一个。

任务单写的是 CHECK。字面 CHECK 和 `ON DELETE SET NULL` 不能同时成立：定时调用没有触发消息，删除时间表时外键把 `schedule_id` 置空会违反 CHECK，删除失败。因此用 `BEFORE INSERT OR UPDATE` 触发器 `agent_invocations_origin`：插入和普通更新仍要求至少一个来源；「原先只有 schedule_id、被外键置空」这一步放行，历史调用留在会话里。集成测试删掉已跑完的 once 后，调用记录还在，`schedule_id` 为空。

### REST（只作用于本人，别人 404）

- `GET /v1/agents/{id}/schedules`
- `POST /v1/agents/{id}/schedules`：`name`、`prompt`、`spec`、`timezone`、可选 `target_conversation_id`（缺省为该 Agent 的专属会话）。主人必须是目标会话成员，否则 `400 not_member`。只读私聊 `400 readonly_dm`。`created_by=user`。
- `PATCH /v1/agent-schedules/{id}`：可改 `name`、`prompt`、`target_conversation_id`、`spec`、`timezone`、`enabled`。改时间表或从停用改为启用时重算 `next_run_at`。
- `DELETE /v1/agent-schedules/{id}`：204。

### 扫描与调用

`enabled AND next_run_at <= now()`。事务里 `FOR UPDATE` 认领：先做准入，不通过就停用并写 `disabled_reason`，不建调用；通过则把 `next_run_at` 推到下一次（`once` 直接停用、`next_run_at` 清空），再插入调用。条件更新保证并发两次扫描只有一个调用。下一次用 `now()` 计算，停机错过的周期不回填。

准入（`schedule::schedule_block_reason`，`schedules::claim_one` 在建调用前调用）：

- 主人 `disabled_at` 非空 → `owner_disabled`
- Agent 已软删除 → `agent_deleted`
- 主人不再是目标会话成员 → `not_member`

**A08 挂点**：合并使用权时只改 `schedule_block_reason`。全局关闭或该用户被禁止时返回 `Some("agent_access")`，管理员始终 `None`。`claim_one` 已经会按返回值停用，不必再改扫描流程。本票没有调用 A08 的检查函数（那一票还在并行）。

调用走现有派发：宿主在线 → `running` + `invocation_start`；离线 → `queued`（A04 的排队截止时间）。`trigger_message_id` 为空，`schedule_id` 为该条目，`context.key = schedule:<id>`，指令是 `prompt`。Agent 回复发到目标会话，正文开头加一行「⏰ 定时任务「<name>」」。

### 工具

`Authorization: Invocation <tools_token>`。只操作这次调用的 Agent、主人本人。

- `GET /v1/agent-tools/schedules`
- `POST /v1/agent-tools/schedules`：体与用户创建相同。`target_conversation_id` 缺省为**发起这次调用的会话**（不是专属会话）。`created_by=agent`。
- `DELETE /v1/agent-tools/schedules/{id}`

宿主 MCP 工具：`create_schedule`、`list_schedules`、`delete_schedule`。

## 4. 未覆盖项与已知限制

- 不做 cron、失败重试、执行历史页。调用记录仍在会话的调用列表里。
- 好友关系解除后，已经建好的、目标是该私聊的定时任务不会在触发时自动停用（任务单只要求主人仍是成员）。只读私聊发不出消息时，调用仍可能标成功但回复被拒绝。
- Agent 软删除不会级联删掉定时任务。扫描到点时停用并写 `agent_deleted`。已删除的 Agent 不能再打开编辑器，这条原因只在库里，列表接口对已删除 Agent 返回 404。
- 间隔上限 5256000 分钟是实现上的防溢出，任务单只写了 N ≥ 5。
- `once` 的 `at` 已经过去时，创建直接 400，不会补跑一次。
- 没有启动 Tauri 窗口。桌面壳只做了 `cargo check`。
- `cargo check` 曾把 `app/src-tauri/gen/schemas/*.json` 标成工作区改动，内容与 HEAD 一致，只是换行。已按 CRLF 写回，`git status` 不再列出这两个文件。

## 5. 发现的其他问题（范围外）

- A13 的 `require_invocation` 用会话 `owner_id` 当主人。群和私聊里这个人和 Agent 主人经常不是同一个，工具会 401。本票改成 Agent 的 `owner_id`，否则定时任务从群里创建、以及定时调用自己再用工具，都会失败。A13 原有测试仍然通过。
