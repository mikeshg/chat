# A22 交付：同一调用的多个并发审批

## 1. 实现摘要

- `server/src/approvals.rs`：`approval_request` 在调用为 `running` 或 `awaiting_approval` 时都建卡，并把调用写成 `awaiting_approval`；`decide` 在还有其他 `pending` 时保持 `awaiting_approval`，没有了才改回 `running`，每张决定都发 `approval_decision`。插入新卡和「最后一张决定后改回 running」共用调用行锁。
- `server/src/domain.rs`：新增 `post_message_in_tx`，让审批卡片和调用行锁落在同一个事务里。
- `server/tests/it.rs`：`// ===== Agent A22 =====` 五条集成测试（两张卡逐张决定、取消全部过期、别的宿主拒绝、宿主断开全部过期、决定最后一张与新请求并发）。

没有改 `agent-host/`、前端、迁移。不需要 `0032`。

## 2. 接口契约

帧和 REST 的形状与 A12 相同，没有新字段、没有新路由、没有新表。

宿主 → 服务端（不变）：

```json
{"type":"approval_request","invocation_id":"...","request_id":"...","tool_call":{"title":"...","kind":"execute","locations":["..."]},"options":[{"optionId":"allow","name":"允许","kind":"allow_once"}]}
```

服务端 → 宿主（不变，每决定一张发一帧）：

```json
{"type":"approval_decision","request_id":"...","option_id":"allow"}
```

行为变更：

- 调用是 `running` 或 `awaiting_approval`，且 `invocation` 属于这条宿主连接：建一张 `pending` 卡（Agent 专属会话，`kind=approval`），调用状态为 `awaiting_approval`。已结束、排队、或宿主对不上：忽略，不建卡、不回帧。
- `POST /v1/agent-approvals/{id}/decide` 的状态码不变（主人以外 404，非 pending 或调用已不是 `awaiting_approval` 则 409 `not_pending`，非法选项 400 `bad_option`）。成功仍返回更新后的 `MessageView`，卡片 `decided`，并推 `message_updated`。
- 成功决定后：该调用还有别的 `pending` → 状态保持 `awaiting_approval`；没有了 → `running`。两种情况都给原会话成员推 `agent_invocation`，并给宿主发上面的 `approval_decision`。
- `expire_invocation` 仍是 `UPDATE ... WHERE invocation_id = $1 AND status = 'pending'`，一次过期该调用上的全部未决卡。

### 加锁顺序

互斥点是 `agent_invocations` 的那一行。两边都在持有这把锁时完成「改审批行」和「改调用状态」，然后才提交。

`decide`（语句没改，仍是 `FOR UPDATE OF ap, i`）：

1. 打开事务。
2. `SELECT ... FROM agent_approvals ap JOIN agent_invocations i JOIN agents a WHERE ap.id = $1 FOR UPDATE OF ap, i`。驱动表是审批主键，行锁顺序是：正在被决定的那张审批行，然后调用行。不锁 `agents`。
3. 校验主人、`pending`、调用仍是 `awaiting_approval`、选项合法。
4. 把这张审批改成 `decided`。
5. 仍持有调用行锁时 `count(*)` 剩余 `pending`。这个数不含刚决定的那张，也看不见还在等这把锁的新插入。
6. 剩余大于 0 → `SET status = 'awaiting_approval'`；否则 `SET status = 'running'`。
7. 抬卡片 `edit_version`，提交。提交之后再推帧、再 `send_to_host`。

`handle_request`：

1. 打开事务。
2. `SELECT ... FROM agent_invocations i JOIN agents a WHERE i.id = $1 AND a.host_id = $2 FOR UPDATE OF i`。只锁调用行。状态不是 `running` / `awaiting_approval` 就回滚返回。
3. 同一事务里 `post_message_in_tx`：锁专属会话行，插入卡片消息，插入新的 `agent_approvals` 行。外键会对调用行要 `KEY SHARE`；此时已经持有更强的 `FOR UPDATE`，不会再升级。
4. 同一事务里把调用写成 `awaiting_approval`，提交。提交之后再推 `agent_invocation` 和卡片消息。

不会和 `decide` 成环：`handle_request` 不锁已经存在的审批行。`decide` 持有「那一张审批行 + 调用行」时，新插入只等调用行。若先插卡再回头把调用行从 `KEY SHARE` 升级到 `FOR UPDATE`，会和正在 `FOR UPDATE` 调用行的 `decide` 死锁，所以锁调用行必须发生在 `INSERT agent_approvals` 之前。

两个事务提交之后不会留下「调用是 `running` 但有 `pending` 卡」：先拿到调用行锁的一方先提交。`decide` 先提交时，若当时没有其他 `pending` 会写成 `running`，随后的 `handle_request` 看到 `running`，在自己的事务里插卡并改回 `awaiting_approval`。`handle_request` 先提交时，`decide` 数得到这张新卡，保持 `awaiting_approval`。

## 4. 未覆盖项与已知限制

- 排队超时只把 `queued` 改成 `timed_out`，不调用 `expire_invocation`。这种调用到不了审批（请求只在 `running` / `awaiting_approval` 时受理），所以没有 pending 卡可过期。取消和宿主断开已用两张卡测过；调用结束（`invocation_finish` 成功或失败）走同一个 `expire_invocation`，没有单独再写一条多卡用例。
- `(invocation_id, request_id)` 没有唯一约束。同一个 `request_id` 再发一次会再插一张卡，决定时两帧的 `request_id` 相同。任务单没有要求去重。
- 并发用例是同一调用上连续 6 轮「决定当前最后一张」与「新 `approval_request`」同时到达，用随后的 `step_start` 确认请求已经处理完，再断言新卡存在且调用仍是 `awaiting_approval`。它能抓住「第二张被丢掉」和「running 但仍有 pending」。它不是穷尽调度的证明。
- 宿主帧仍是 `try_send`。宿主不在线或发送队列满时，`approval_decision` 会丢。这是 A12 的原行为。
- 审批卡怎么展示、宿主要不要把多次审批串行化，按任务单不做。

## 5. 发现的其他问题

对 `awaiting_approval` 的检索（`agents.rs`、`agent_tools.rs`、`approvals.rs`、`host_ws.rs`）里，单审批假设只在 `approvals.rs` 的两处，已经改掉：

- `agents.rs`：取消、删除 Agent、收回使用权、级联取消、`invocation_finish` 都调用 `expire_invocation(调用 id)`，按调用过期全部 `pending`，不按一张卡。`awaiting_approval` 与 `running` 一样视为进行中。
- `agent_tools.rs`：调用凭据在 `running` 和 `awaiting_approval` 都有效。多张卡期间状态一直停在 `awaiting_approval`，工具通道保持可用，宿主才能在等第一张批准时再发下一次审批。
- `host_ws.rs`：断开时把该宿主全部 `running` / `awaiting_approval` 调用改成 `failed/host_disconnected`，再对每个调用 `expire_invocation`。

没有为此改这三个文件。
