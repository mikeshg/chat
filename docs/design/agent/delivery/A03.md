# A03 交付：三种输出方式 + 调用状态标签

对应 Gitea issue `xiefan/chat#4`。迁移号 `0024_agent_steps.sql`。

## 1. 实现摘要

### 宿主运行时（`agent-host/`）

- `src/runtime.rs`：`RunEvent` 加 `StepStart { id, title, kind }` / `StepEnd { id, ok }`；`RunOutput` 加 `steps: Vec<StepRecord>`（`{id,title,kind,ok}`）。
- `src/acp.rs`：`tool_call`（toolCallId/title/kind）→ `StepStart`；`tool_call_update` 的 `status` 为 `completed`→`StepEnd{ok:true}`，`failed`/`stopped`→`StepEnd{ok:false}`（`stopped` 一并算失败终态，防止步骤永久挂起）。进行中步骤存 HashMap，完成步骤累积进 `RunOutput.steps`；单步失败不拖垮整个调用。
- `src/conn.rs`：每次调用建事件 channel，`forward_events` 把 `RunEvent` 转成 `invocation_event` 帧发服务端；连续文本增量按 100ms 窗口合并，步骤事件前先冲刷滞留文本（保证文本先于步骤到达）；`invocation_finish` 携带 `text` + `steps`。新增 2 个单元测试（100ms 合并、步骤前冲刷）。
- `tests/fake-acp-agent.mjs`：新增 `steps:<N>`（N 个 `tool_call`+文本+`tool_call_update completed` 穿插，最后回 `done`）、`stepfail`（一步 `failed` 后正常 `done`）、`drip:<ms>`（每 ~30ms 一个小 chunk，服务端限频验证用）。
- `tests/acp.rs`：新增 `acp_steps_emit_start_end_events`、`acp_stepfail_emits_failed_end`。

### 服务端（`server/`）

- `migrations/0024_agent_steps.sql`：`messages.agent_steps jsonb NULL` + CHECK（NULL 或数组）；重建 `message_views`，末尾追加 `agent_steps`（同 0019 写法）。
- `tests/migrations.rs`：迁移列表追加 0024。
- `src/model.rs`：`AgentStepView`/`StreamStepView`；`MessageView.agent_steps`；`InvocationView.current_step`（`#[sqlx(default)]`，内存回填不落库）；`WsOut::AgentStream`。
- `src/state.rs`：`InvRun`（host_id/会话/成员/调用快照/生效输出方式/进行中步骤/已完成步骤/流式缓冲/冲刷节流标记）；`AppState.inv_runs: DashMap<Uuid, InvRun>`。
- `src/domain.rs`：`PostMessage.agent_steps` + INSERT（仅 `agent_id` 非空时可写步骤列）；`MsgViewRow`/`into_view`/`list_conversations` 的 last_message 子查询均带 `agent_steps`。
- `src/agents.rs`：
  - `dispatch` 时用 `effective_settings` 取生效 `output_mode`，连同调用快照登记 `inv_runs`（先于 `invocation_start` 下发）。
  - 新增 `handle_event`：校验 `invocation_id` 属于本宿主连接的进行中调用（伪造/迟到一律忽略）；按模式分发——stream 推 `agent_stream` 帧（delta 每 200ms 至多一帧，延迟冲刷任务兜底；step 顺带冲刷积压 delta）；status 推带 `current_step` 的 `agent_invocation`；steps 每步结束写一条 `✓/✗ <title>` Agent 消息。
  - `handle_finish`：摘下 `inv_runs`；先冲刷滞留 delta 再落定稿消息；`agent_steps` 优先取 finish 帧的权威 steps、缺省退回事件累积（steps 模式正文不带步骤列）；失败置 `failed`+error。
  - `list_invocations`：running 调用回填内存 `current_step`。
  - `host_ws.rs`：路由 `invocation_event` 到 `handle_event`；宿主断开收尾时摘除其 `inv_runs`。
- `src/ws.rs`/`src/api.rs`：必要的帧分发与查询列接入。
- `tests/it.rs` 末尾新增 `// ===== Agent A03 =====` 一节 6 个测试：stream（stream 帧有序、历史无中间内容、定稿带 2 步）、status（无 stream 帧、running 帧带 current_step、终态清空）、steps（每步一条 ✓ 消息 + 正文）、stepfail（步骤 ok=false 而调用 succeeded）、限频（agent_stream 帧数 ≤ 时长/200ms + 余量）、伪造 invocation_event 被忽略。

## 2. 接口契约

### 表结构（`0024_agent_steps.sql`）

- `messages.agent_steps jsonb NULL` + CHECK `agent_steps IS NULL OR jsonb_typeof(agent_steps)='array'`；元素形如 `{id,title,kind,ok}`。
- `message_views` 重建，末尾追加 `agent_steps`（列序其余照旧）。

### WS 帧

- 宿主→服务端：`{type:"invocation_event", invocation_id, event:{type:"text",text} | {type:"step_start",id,title,kind} | {type:"step_end",id,ok}}`；`invocation_finish` 加可选 `steps:[{id,title,kind,ok}]`。
- 服务端→成员：`{type:"agent_stream", invocation_id, conversation_id, delta?, step?}`（stream 模式，delta 与 step 至少有一个）；`agent_invocation` 的 `InvocationView` 加可选 `current_step`。
- 与任务单无契约偏差。`tool_call_update` 的 `stopped` 也映射为 `ok:false`（任务单只列 completed/failed；stopped 同为终态，不映射会让步骤永远挂起）。

## 4. 未覆盖项与已知限制

- 取消/排队/超时/审批状态、子调用嵌套：任务单声明归 A04/A12/A15，状态标签已做成查表组件供 A04 直接加项。
- 任务单浏览器实测写的是「各发一次 `steps:3`」；实际用了 `steps:2`/`drip:900`/`sleep:1500`/`stepfail` 组合，覆盖面更全（含流式增量与失败步骤），语义等价。
- `current_step` 的浏览器端验证覆盖在 it.rs（帧断言）；假 agent 没有「长时间挂起的步骤」指令，浏览器只断言了状态行出现/消失。
- stream 模式的 `agent_stream` 是临时帧不落库：刷新后只剩定稿消息（符合任务单「不重复出现增量」）。

## 5. 发现的其他问题（范围外）

- 浏览器实测发现并顺手修了一个本票内的真实 UI 缺陷：定稿消息带步骤记录时，气泡悬浮操作条（`.msg-actions`，`top:-15px`）会盖住「N 个步骤」摘要按钮导致无法点击展开；已用 `.step-record + .bubble-wrap > .msg-actions { top: 0 }` 修正（步骤记录存在时操作条收进气泡内缘）。
