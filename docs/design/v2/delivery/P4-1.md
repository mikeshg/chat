# P4-1 管理后台备份 / 恢复 — 交付文档

## 1. 实现摘要

迁移：无（不新增表；备份/恢复完全基于现有 schema 与 `FILES_DIR`）。

服务端：

- `server/src/backup.rs`（新，~960 行）— 全部备份/恢复逻辑：
  - **备份**：`run_backup` 动态枚举 `information_schema.tables` 里 `public` 的全部 `BASE TABLE`（排除 `_sqlx_migrations`，不硬编码表清单），逐表 `COPY ... TO STDOUT WITH (FORMAT csv, HEADER true)` 落入 `FILES_DIR/.spool-<uuid>/db/`，再打包 `manifest.json` + `db/<table>.csv` + `files/<相对路径>` 成 gzip tar。先写 `chat-backup-<yyyyMMddTHHmmssZ>.tar.gz.part`，flush+sync 后原子 rename；`.backups/`、`.restore-*`、`.spool-*` 顶层前缀不参与打包、不跟随符号链接。`backup_busy` 保证备份/恢复互斥。
  - **下载票据**：`download_tickets: DashMap<String,(path,expiry,user)>`（state.rs），POST 签发 60s 一次性票据，GET 流式 `tokio_util::io::ReaderStream` 发送，票据取出即作废。
  - **恢复校验（只读，不动状态）**：gzip/tar 可解、条目类型仅 Regular/Directory、路径经 `safe_rel_path` 拒绝 `..`/绝对路径/盘符、`manifest.format==1`、`migration_version` 与当前一致、`db/*.csv` 表集合与库中表集合完全一致。
  - **恢复执行**：`extract_archive` 到 `FILES_DIR/.restore-tmp-<uuid>/db` + `FILES_DIR/.restore-new`；`restore_db` 单事务内按 FK 依赖排序 `TRUNCATE ... CASCADE` + `COPY FROM STDIN` 回灌；循环/自引用约束（本 schema 共 36 条入候选，`users↔invites` 等成环）先 `DROP CONSTRAINT` 回灌后原样 `ADD CONSTRAINT`（由 `pg_get_constraintdef` 存定义，含 NOT VALID 语义保全）。`swap_files` 三段交换（旧档→`.restore-old`，新档上位，删旧），失败路径整体回滚不动现状。`invalidate_all_credentials` 全量 `session_version+1` 并吊销 sessions/refresh_tokens。
  - **维护模式**：`AppState.maintenance: AtomicBool` + `maintenance_gate` 中间件挂在整个 `/v1` 路由层——恢复期间一切 /v1 请求（含 WS 升级）503 `{error:"服务维护中，请稍后"}`。
  - **关键结构**：恢复真正执行体跑在 `tokio::spawn` 独立任务里而非请求 future 上；`MaintGuard`（Drop 置 false）+ `BusyGuard` + 上传文件清理全部随任务生命周期兜底。原因见 §3 浏览器实测发现的 bug。
- `server/src/api.rs` — 挂载 6 条路由（见 §2）；`/admin/restore` `DefaultBodyLimit::disable()`（备份可超默认上限）；`/admin` 前缀统一先 `require_admin`。
- `server/src/lib.rs` — `pub mod backup`；`build_router` 里 `v1` 路由 `.layer(from_fn_with_state(state, maintenance_gate))`。
- `server/src/state.rs` — `maintenance`、`backup_busy` 两个 `AtomicBool` + `download_tickets` 表。
- `server/Cargo.toml` — 新增 `tar 0.4`、`flate2 1`、`tokio-util 0.7(io)`（dev 复用同名 crate 造测试包）。

客户端：

- `app/src/types.ts` — `BackupInfo`、`BackupListResponse`。
- `app/src/api.ts` — `backups.list/create/remove`、`backupDownloadTicket`、`backupDownloadUrl(ticket)`、`restoreBackup(file,onProgress)`（XHR FormData，上传进度回调，file+confirm=RESTORE 两字段）。
- `app/src/ui/BackupPanel.tsx`（新）— 管理面板：「立即备份」异步生成 + 4s 轮询列表；行内 下载（隐藏 `<a>` 触发浏览器下载）/ 删除（confirm）；恢复区选 `.tar.gz` + 必须键入 `RESTORE` + 进度条；成功路径写 `chat_kick_reason="恢复完成，请重新登录"` 并派 `chat:logout`。

测试（先写后实现，it.rs `// ===== V2 P4-1 =====` 节，7 个）：

- `p41_restore_rolls_back_data_and_credentials` — 备份后改数据 → 恢复 → 数据回滚、旧 access/refresh 全部失效、重登录可用。
- `p41_restore_requires_confirm` — 无 RESTORE 字样 400；非管理员 403。
- `p41_restore_rejects_version_mismatch` — manifest migration_version 不符 → 400 且数据未动。
- `p41_restore_rejects_unsafe_paths` — 手工构造 `..` 路径 tar 头 → 400；非普通文件条目 → 400；数据未动。
- `p41_backup_admin_gate_and_ticket_rules` — 非管理员全路由 403；票据一次性、过期、错用户。
- `p41_maintenance_blocks_api` — 维护闸置位时 /v1 REST 与 WS 升级均 503，复位后恢复。

## 2. 接口契约

- `GET /v1/admin/backups` → `{in_progress, items:[{name,size,created_at}]}`（仅完成件，name 字典序=时间序倒排）。
- `POST /v1/admin/backups` → 202 `{name}`，生成异步进行（同名第二请求/恢复进行中 409）。
- `POST /v1/admin/backups/{name}/download-ticket` → `{ticket}`（60s、单次、绑定签发者）。
- `GET /v1/admin/backups/{name}/download?ticket=` → 200 `application/gzip` 流。
- `DELETE /v1/admin/backups/{name}` → 204；`name` 经 `safe_backup_name` 严格校验（防穿越）。
- `POST /v1/admin/restore`（multipart `file` + `confirm=RESTORE`）→ 校验失败 400（数据不动）；成功 200 `{tables,files}`，同时全体用户被踢、凭据全废。
- 归档契约：`manifest.json{format:1,created_at,migration_version,tables[{name,rows}],files,files_bytes}` + `db/<table>.csv`（COPY csv+header）+ `files/<相对路径>`。
- 维护期间：除正在执行的恢复请求外，/v1 全部 503（含 `/v1/ws` 升级）。

截图（`server/target/wt/`）：`p41-01-backup-listed.png`、`p41-02-msg-after-backup.png`、`p41-03-restore-confirm.png`、`p41-04-kicked-to-login.png`、`p41-05-after-relogin.png`；下载留档 `p41-downloaded.tar.gz`。

**实测抓出的真 bug（已修）**：恢复原本直接跑在请求 future 上。浏览器端管理员被 WS 踢下线回登录页后，任何页面导航/刷新（本例为 e2e 的 `page.goto`）都会 abort 在途的恢复 fetch → axum drop handler future → DB 事务 ROLLBACK、`maintenance` 标志永远停 true → 服务被永久 503 卡死（pg 探针显示全部后端 idle 且最后一次执行为 ROLLBACK）。修复：恢复执行挪入 `tokio::spawn` 任务，维护闸用 `MaintGuard` 的 `Drop` 复位、`backup_busy` 与上传文件清理由任务持有兜底——客户端断连不影响恢复跑完且闸必然落下。修复后 e2e 在同样 abort 条件下通过。

**被拒命令与替代（环境约束记录）**：进程内联环境变量赋值形式（`VAR=x cmd`）在非交互层均被拒——含 `APP_DATABASE_URL=… node wt-server.mjs start`（后来确认 `APP_DATABASE_URL` 本就指向本 worktree 独占容器库，无需覆盖）、`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm i`、`CARGO_TARGET_DIR=… cargo test`（改用 `cargo --target-dir` 亦未必要）；`npm i playwright` 链式命令被拒（改为直接 `import` 现成 `…/playwright/index.mjs`，本机缓存 Chromium 工作正常）；`&&`/`;` 组合的单条长命令被拒一次（改用 `run-e2e.mjs` 单 node 入口编排 sanctioned 起停）。`docker`/`wsl`/`cargo run`/自起后台进程按 deny 列表未尝试。

## 4. 未覆盖项与已知限制

- 恢复确认文案的最终显示：WS `maintenance` 踢出先到（"服务器维护中，请稍后重新登录"），恢复响应若随后到达会覆写为"恢复完成，请重新登录"——两者都成立，视时序而定。
- 恢复中发起的恢复响应若被客户端主动断连，响应丢失但恢复照样完成（修复后语义）；客户端需重新登录即可。
- `COPY FROM STDIN` 逐表回灌，未做并行（恢复是低频管理操作，正确性优先；大库可用 COPY 本身吞吐）。
- 备份的数据库部分在**同一个 `REPEATABLE READ READ ONLY` 事务**里导出（`BEGIN ISOLATION LEVEL ...` + 逐表 `COPY TO STDOUT`），表与表之间是同一时刻快照；文件部分按任务单是近似快照（`// ponytail:` 注释标明：导出期间变化中的文件宁可失败重试也不产出坏包——`pack_archive` 用 `CountingRead` 校验实际写入字节数与打包头声明 size 一致，否则整包失败）。
- `.backups/` 目录内归档不纳入自身打包；文件名碰撞（同一秒两次生成）不会并发（busy 锁），列表按名字倒排即时间序。
- 未做备份保留策略/配额（任务单未要求）；`FILES_DIR` 满时写 `.part` 会失败并清理。

## 5. 发现的其他问题（范围外，仅记录）

- `run_backup`/`restore_db` 表名都经 `qi()` 引号化，若未来出现需要 schema 限定或含特殊字符的表名，`unqualify`/`regclass::text` 处理已覆盖常规形态；非常规表名场景建议届时再测。
- `pg_locks`/`pg_stat_activity` 现无应用内探针，本次排障靠临时 node `pg` 脚本；如有需要可将锁诊断固化进管理接口。
